## Pivotal finding: X (observable) vs Y (ledger-only) — **openinference `llm.input_messages` channel only**

**VERDICT: Y — ledger-only structural canary ORACLE (upper bound) — FOR THE openinference `llm.input_messages` CHANNEL.**

> ⚠️ Scope: this verdict is about that ONE channel. A SECOND channel — the injector's post-pruning `agentfault.resolved_input` span attribute — was added afterwards and DOES make the deletion observable on this dataset (n=36, Hit@1 = 1.000; see the source-split section below). Do not quote the Y verdict as "context_drift is unobservable".

Evidence (re-derived at runtime by parsing the captured spans directly — no `injector_smoke` import, which has import-time env side effects):

- Per-agent LLM **input** prompts ARE captured in spans (openinference `llm.input_messages.*` on the `ChatOpenAI` child spans): **True**.
- Yet in the drift cases the DROPPED upstream message is still PRESENT in the TARGET agent's captured input (name match):

| scenario | target agent | dropped upstream | traces | dropped-msg PRESENT | ABSENT |
|---|---|---|---|---|---|
| `ctxdrift_ub_from_seq` | User_Behavior_Analyzer | Sequence_Recommender | 13 | 13 | 0 |
| `ctxdrift_prod_from_ub` | Product_Analyzer | User_Behavior_Analyzer | 13 | 13 | 0 |
| `ctxdrift_synth_from_prod` | Recommendation_Synthesizer | Product_Analyzer | 13 | 13 | 0 |

  Totals: dropped-msg present in **39/39** target-agent traces.

**Mechanism (why the deletion is invisible in captured data):** the injector (`_maybe_context_drop`) deletes the upstream `HumanMessage` INSIDE the patched `ChatOpenAI._generate` (`messages[:] = kept`), i.e. AFTER LangChain's `on_chat_model_start` callback — which is what openinference uses to record `llm.input_messages` — has already fired in `BaseChatModel.generate()`. So the span records the **pre-deletion** message set. The content-layer input is captured, but at the wrong point: it reflects what the pipeline assembled, not what the model actually received after pruning.

**Consequence (this channel only):** the deletion cannot be observed **through `llm.input_messages`**. A locator restricted to that channel is therefore labeled exactly as:

> structural canary ORACLE (deterministic upper bound; injection-point-visible signal sourced from the injection ledger; a real detector would reconstruct it from per-agent input-message structure, which requires capturing per-agent input prompts that reflect the post-pruning message set actually sent to the model — a known instrumentation gap)

Restricted to this channel it mirrors Tier-A's contract-oracle framing: a deterministic, injection-visible upper bound — NOT a learned or observable method. A real trajectory monitor could reconstruct the canary only if the per-agent input were captured post-pruning (the message set actually sent to the model), comparing each agent's received upstream-message names against the fixed pipeline's expected upstream set and flagging the agent missing an expected upstream message. **That capture gap has since been CLOSED** by the injector's `agentfault.resolved_input` emission — see the next section for the genuine observable detector.

## Observable detector vs oracle fallback (source split — NOT merged)

The injector now emits the POST-pruning received-message names into the trajectory (span `agentfault.resolved_input`, attr `agentfault.resolved_input.msg_names`). The detector reads that and applies the chaosgraph `AllRequiredNodesVisited` set-diff (`missing = expected_upstream − received`) — a GENUINE observable method. When the attribute is ABSENT (old / un-recollected data) the case falls back to the ledger-sourced ORACLE (upper bound). The two are reported separately and never merged.

- source split: `{'observed_detector': 36}`
- **observable detector** (genuine): Hit@1 = **1.000** over **n=36** cases carrying the attribute.
- **oracle fallback** (upper bound): Hit@1 = **N/A** over **n=0** attribute-absent cases.

conv-len anomaly by scenario: `ctxdrift_prod_from_ub`=0.417, `ctxdrift_synth_from_prod`=0.000, `ctxdrift_ub_from_seq`=0.833.

**Honest reading of the conv-len number (do not overclaim it as ~random).** Overall Hit@1 = 0.417, above the 0.250 floor — BUT it is wildly scenario-unstable (0.417 / 0.000 / 0.833 across the 3 scenarios; spread 0.833) and therefore NOT a dependable locator. It scores its worst, 0.000, on `ctxdrift_synth_from_prod`: the Synthesizer's output is a templated tool-call whose length barely moves, so the anomaly ranker never picks it; and its best, 0.833, on `ctxdrift_ub_from_seq` because the analyzer's free-text length happens to swing most there. The signal is tracking **which agent emits the most variable free text, not the drop** — its overall is carried by one scenario, not localization skill. Under group-aware CV the very same conv-len feature set collapses to Tier-A RF-content 0.000.

**Thesis:** context_drift leaves NO latency signature (the system recovers) and NO needle/asin/contract signal, and per-agent OUTPUT text-length is at best an unstable, scenario-dependent proxy (0.000 where the target is the Synthesizer) — no output-content or infra method is a reliable localizer. Only the INPUT-structure canary (which requires the pre-call injection point / post-pruning input capture) localizes it dependably — and on this dataset that canary IS observable: the post-pruning `agentfault.resolved_input.msg_names` attribute carries it for n=36 of the 36 cases (Hit@1 = 1.000), with the ledger-sourced ORACLE fallback used on n=0 cases.
